# Bitrefill V1.3 purchase persistence — local design and gate status

Status: **PARTIAL / LOCAL DB CANDIDATE — NOT READY FOR PURCHASE OR PRODUCTION MIGRATION**. The migration was applied only to disposable local PostgreSQL 17.11 databases, not Production or the existing business Test database. The real Bitrefill HTTP transport remains GET-only. The tables grant `service_role` read access only; narrowly granted security-definer RPCs now provide local transactional writes, but the application does not call them. This is not evidence of production recovery.

## Existing model and reuse

`supplier_fulfillment_requests` already has `unique(order_item_id)`, `unique(request_id)`, a transactional claim RPC, attempt token/count, status including `UNCERTAIN` and `RECONCILIATION`, one `provider_order_code`, frozen binding verification, and cost fields. The generic outcome RPC atomically creates one `order_deliveries` row and its `digital_delivery_secrets` entry. `order_deliveries_supplier_item_delivered_uidx` enforces one successful supplier delivery per Jianlian order item. Daju's live route and local-inventory-first policy are unchanged. These structures must remain the root and delivery boundary; no second order state machine or secret store is justified.

The gap is real: one root row and one external reference cannot losslessly store one invoice shared across many items, multiple child orders/units, split invoices, authoritative GET history, a durable post-submit boundary, or webhook receipt dedupe. A future migration must add only these provider-neutral relations and safe evidence. The existing `UNCERTAIN` state alone is insufficient if an invoice ID has not yet been persisted. No native Bitrefill purchase idempotency key or merchant reference has been verified; a possibly sent POST must never be blindly retried.

## Offline contracts implemented

`evaluateSupplierAvailability` defines `AVAILABLE`, `UNAVAILABLE`, and `UNKNOWN` with separate exact `quantity` and `quantityKnown` evidence. Quantity `5` remains an exact quantity; boolean `in_stock=true` remains available with `quantity=null`; stale/error/malformed evidence becomes `UNKNOWN`. The new V1.3 SQL replacement for the P2.3 evaluator preserves Daju's quantity path and accepts Bitrefill only with explicit, fresh, consistent boolean metadata. No application path currently persists that exact metadata contract or enables Bitrefill purchase, so this SQL gate does **not** activate any SKU. Apple US remains an offline target, not a binding.

`buildSupplierPurchaseIdentity` computes a versioned SHA-256 semantic hash from frozen non-secret identity fields (provider, order item, request/attempt identity, product/package, quantity, exact decimal amount, currency). The local claim RPC now persists a supplied hash and validates paid/nonterminal order state, frozen order snapshot, package, quantity slice, currency, face value and cost ceiling in one transaction. This is not production idempotency until the application uses that RPC before any HTTP request. `classifySupplierSubmitBoundary` still defines the no-blind-retry rule: an ambiguous post-submit outcome without an external ID is `UNCERTAIN` and requires manual reconciliation.

Live-observed HTTP 403 with `error_code=not_available` is now classified as `PRODUCT_NOT_AVAILABLE_IN_CURRENT_CONTEXT`, not an authentication failure. Generic 403 remains `FORBIDDEN`. The 149/200/201 package bounds and text-package purchase block have regression coverage. Apple US mapping, trusted cost, Business API approval and credentials all remain unavailable; no supplier binding was written.

## Isolated local PostgreSQL evidence (2026-10-15)

The [candidate migration](../../supabase/migrations/20261015063415_supplier_purchase_persistence_v1_3.sql) was created with Supabase CLI 2.121.0, then applied to `jianlian_bitrefill_v13_test` at `127.0.0.1:55433`. The database data directory is `D:/Jianlian/_bitrefill_v13_local_pg/data`; it was initialized from the checksum-verified EnterpriseDB PostgreSQL 17.11 portable archive and started directly as a user process, without a Windows service or firewall change. The official EDB archive SHA-256 was `b9424ee7bc60b52450ff910a3630225df32e633f3cb29c1d126d9299d59aea28`; the downloaded archive matched. The official Supabase CLI release checksum for its Windows archive matched `bc0f27a29c1f4ccaf33a801b7cb9d10da6484568c88e232c9dea0b9e8666b0db`. Neither archive is in Git.

The migration adds provider-neutral `supplier_purchase_attempts`, per-unit `supplier_purchase_attempt_items`, `supplier_external_orders`, `supplier_webhook_receipts`, and `supplier_reconciliation_evidence`. Existing `supplier_fulfillment_requests` remains the order-item root, while `order_deliveries` and `digital_delivery_secrets` remain the sole delivery path. The attempt stores a semantic request hash and durable `CLAIMED`/`SUBMITTING`/`UNCERTAIN`/external-ID states. One attempt maps to one external invoice; frozen unit rows map exact order-item units, with a trigger checking root supplier/product/package and a 20-unit cap. External child rows uniquely identify supplier order IDs and map to one frozen unit; a trigger rejects misassigned child orders or delivery IDs for another order item. Unique indexes block duplicate logical requests, external invoice IDs, child IDs, frozen units and webhook fingerprints. All five tables have RLS enabled, no browser policy and no anon/authenticated privileges. Service role has SELECT only on tables and EXECUTE only on five scoped write RPCs. No secret, raw authenticated response, authorization header or redemption plaintext field was added.

The [minimal-base fixture](../../tests/support/supplier-v13-isolated-base.sql), [constraint checks](../../tests/support/supplier-v13-isolated-constraints.sql), [concurrency probe](../../tests/support/supplier-v13-isolated-concurrency.mjs) and [1000-row query plans](../../tests/support/supplier-v13-isolated-explain.sql) passed against that real local PostgreSQL. Direct `SET ROLE` queries denied `anon` and `authenticated` SELECT, allowed `service_role` SELECT and denied `service_role` INSERT. The five requested lookup classes selected their intended indexes in the 1000-row EXPLAIN fixture. These tests use a deliberately narrow synthetic Supplier Core base, not the complete 124-file Supabase migration history, and do **not** establish full-schema clean apply, delivery RPC atomicity, real reconciliation behavior or application restart safety.

## Remaining required contract

The [schema plan](bitrefill-purchase-schema-plan.md) remains the design source. Local RPCs now claim, transition, register child IDs, write safe reconciliation evidence and dedupe webhook receipts. They perform no HTTP. The application still lacks the server-only transactional call path, persistent worker recovery, authenticated GET reconciliation wiring, private-secret delivery integration and two-worker delivery E2E. A successful invoice must never be treated as every child delivered. The boolean SQL evaluator is not an operational activation route: no persisted Bitrefill SKU metadata writer or approved binding exists, and real purchase capability remains disabled. The Apple 10-SKU target stays unchanged.

The [production precheck draft](sql/bitrefill-v1-3-production-precheck.sql) is read-only and was not executed against Production. A local full-baseline replay started with the repository's `schema.sql`, `orders-schema.sql` and migration order, but stopped at the known malformed SQL string in historical `20260622_digital_delivery_hardening.sql:188`; no old migration was altered or skipped. Thus `FULL_BASELINE_REPLAY_PASS=no`. A separate clean narrow fixture applied the revised V1.3 migration and exercised the RPCs. Two DB connections racing on the same child fingerprint produced one evidence row; two racing delivered-row inserts for one order item produced one winner under the existing unique index. This proves database primitives, not complete private-secret delivery. A dirty fixture with duplicate existing provider invoice IDs aborted at the explicit preflight and left zero new purchase tables. These are **partial local DB proofs**, not a full Supabase baseline, application restart, complete delivery or production equivalence. Do not push this branch as production-ready V1.3.
