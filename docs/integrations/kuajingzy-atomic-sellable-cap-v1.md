## Capacity lifecycle

For a verified frozen KuajingZY binding, product_skus.stock is the local sellable cap. Upstream supplier_stock_snapshot is advisory evidence. This migration never copies that snapshot into website stock.

The existing create_order_with_item transaction conditionally decrements the exact SKU before inserting the item. Product and SKU row locks, the existing request advisory lock, and the conditional UPDATE protect capacity. A failed UPDATE raises KUAJINGZY_SELLABLE_CAP_EXHAUSTED and rolls the entire order transaction back. The API maps only that exact message to HTTP 409 with KUAJINGZY_ORDER_UNAVAILABLE before payment creation.

The item snapshot freezes sellable_cap_reservation with version 1, MODEL_C, kuajingzy, exact SKU, quantity, and reserved=true. Request replay returns the existing order before decrement. Unknown supplier declarations fail closed.

Unpaid cancel and expiry restore capacity through release_order_inventory. The existing order row lock and reservation_released_at serialize releases. Only exact markers on automatic items with matching SKU and quantity, a known unpaid/releasable lifecycle, and no delivered order_delivery qualify. Historical items without markers restore zero capacity. The released_kuajingzy_cap diagnostic counts restored SKU rows independently of digital inventory.

Restoration changes sold_out to active. Draft, inactive, disabled and other statuses are preserved. Paid orders consume capacity permanently in V1, including unresolved procurement failure or manual review. Successful fulfillment also consumes capacity. Automatic replenishment is outside V1.

## Disposable PostgreSQL 17 verification

The standalone tests/integration/kuajingzy-atomic-sellable-cap-pg17.mjs runner requires explicit loopback settings and the kuajingzy_freeze_isolated database. The GitHub workflow supplies a disposable postgres:17 service. The runner creates synthetic objects in an empty database and rejects other endpoints and PostgreSQL major versions.

Concurrent independent connections reach a database advisory barrier before the real RPCs execute. Tests cover caps 1 and 2, over-cap quantity, concurrent request replay, cancel and expire, concurrent release, paid/final states, exact and malformed markers, historical orders, delivered items, status preservation, item-insert rollback, ordinary SKU/product stock, local digital inventory, Daju, Bitrefill, unknown suppliers, source drift and ACL preservation.

The generator tests/support/generate-kuajingzy-atomic-cap.mjs uses the same empty local database restriction to regenerate the candidate. Its bootstrap deliberately requires an empty disposable database.
